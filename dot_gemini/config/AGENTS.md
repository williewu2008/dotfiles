# 全域 Agent 協作規範與指引 (Global AGENTS.md)

本文件為全域 Agent 協同規範，適用於本機環境下所有的專案與工作區。

---

## 1. 核心協作工作流 (Standard Workflows)

### 🌅 開工流程 (Start of Work)
當使用者提到「開工」或展開新任務時：
1. **讀取規範與脈絡**：讀取專案根目錄的 `ANTIGRAVITY.md`、`agents.md` 或主要說明文檔。
2. **檢視進度**：檢查專案筆記、工作看板（Kanban）與當前任務。
3. **版本控制檢查**：執行 `git status` 並檢視最近的 commit 紀錄。
4. **狀態回報與規劃**：向使用者回報當前進度與建議的下一步。
5. **安全原則**：**不自動** 執行 pull、commit 或 push，任何版本異動需經確認。

### 🌇 收工流程 (End of Work)
當使用者提到「收工」或階段性任務告一段落時：
1. **敏感資料審查**：嚴格檢查變更內容，確保無任何 API Key、Token、密鑰或個人機密外洩。
2. **同步專案筆記**：更新專案進度、工作藍圖（如 `agents.md`）、已完成事項、下一步與踩坑記錄。
3. **規範維護**：僅在協作規則實質調整時更新 `ANTIGRAVITY.md` 或本文件。
4. **檢查差異**：執行 `git status` 與 `git diff` 審查所有異動。
5. **精準 Stage**：**嚴格禁止無差別 `git add .`**，只 stage 本次相關檔案。
6. **確認後 Commit & Push**：確認 commit 訊息符合語意化規範（Conventional Commits），經確認後提交並推送。
7. **回報同步結果**：回報最終 commit hash 與遠端同步狀態。

### 🚀 新專案初始化流程 (Project Initialization)
當使用者要求「初始化專案」或「新專案初始化」時：
1. **先確認需求**：詢問專案名稱、主要用途、存放目錄、是否建立 GitHub 儲存庫（公開/私人）以及是否有部署需求。
2. **標準檔案建立**：
   - `ANTIGRAVITY.md`：專案規範與工作流
   - `agents.md`：專案工作藍圖與看板
   - `README.md`：專案導覽
   - `.gitignore`：標準環境與敏感檔案過濾
   - 專案筆記目錄（如 `notes/`）與 Git 初始化
3. **不破壞既有結構**：若專案已存在檔案，盤點後僅補充缺口，不任意覆蓋。

## 2. 語音回覆規範 (Voice Responses via Edge-TTS)

本環境統一使用 **Edge-TTS**（免費、微軟雲端語音合成）作為語音回覆工具。不使用 SAPI 離線語音、不使用外部播放器視窗。

1. **觸發時機**：當使用者提及「用語音回答」「唸出來」「唸給我聽」「用語音講結論」時執行。
2. **講稿撰寫**：
   - 口語化、精簡（100–250 字）。
   - 數字用中文（例如「五十頁」而非「50頁」）。
   - 只講核心結論與下一步，詳細資料保留於文字回覆。
3. **聲音選擇**：
   - 預設使用 `zh-TW-YunJheNeural`（男聲，穩重自然、適合教學）。
   - 備用聲音：`zh-TW-HsiaoChenNeural`（女聲活潑清晰）、`zh-TW-HsiaoYuNeural`（女聲溫柔）。
   - 使用者明確指定其他聲音時才切換。
4. **播放方式**：一律以本機行內音訊播放（例如透過 PowerShell `PresentationCore.MediaPlayer`），**不開啟外部播放器視窗**。
5. **播放結束**：簡短回報「語音已播放」，不重複贅述完整文字內容。

## 語音輸入文字正規化

使用者可能以語音輸入，文字中可能出現同音錯字、詞界切分錯誤、標點遺失、英文工具名稱音譯，以及路徑或指令辨識錯誤。

- 先依對話上下文理解使用者最合理的原意，不要逐字死讀。
- 明顯且不影響實際行動的小錯字，直接理解並繼續，不要逐項糾正或打斷使用者。
- 工具名稱可能被音譯或誤辨識。例如在 AI Agent 情境中，`Call Desk` 可能是 `Codex`、`Cloud Code` 可能是 `Claude Code`、`scheme` 可能是 `Skill`。這些只是語境提示，不得在所有情況下強制替換。
- 如果模糊內容會影響實際行動，例如人名、檔名、路徑、指令、工具名稱、數字、日期、金額或核心需求，而且無法從上下文可靠判斷，先用一句話確認理解，再執行。
- 不要默默把關鍵資訊改成猜測版本後直接執行。
- 不要捏造使用者沒有說過的數值、路徑、日期、名稱或授權。
- 回覆時使用自然、修正後的語意即可；除非使用者詢問，否則不必列出所有辨識錯字。

## 4. 安全性與隱私邊界 (Security & Privacy)

- **金鑰防護**：絕對不將 API Key、Personal Access Token、憑證或密碼寫入 Markdown、程式碼、版本控制或對話紀錄中。
- **敏感檔案排除**：環境變數一律使用 `.env.example` 示意，並確保 `.gitignore` 涵蓋 `.env*`、`*.key`、`*.pem`、`credentials.json` 等。
- **操作審慎**：高風險操作（如資料庫刪除、強制推送 `git push -f`、永久刪除檔案）必須主動向使用者請求明確確認。

---

## 5. 程式碼品質與文檔原則 (Code & Documentation)

- **語言與風格**：中文溝通與文檔預設採用繁體中文（台灣用語習慣），技術術語保持精準。
- **文檔結構化**：善用 GitHub 風格 Markdown、架構圖（Mermaid）、任務清單與表格，提升可讀性。
- **檔案路徑超連結**：在提及工作區內的檔案與代碼符號時，使用可點擊的 markdown 連結（如 `[filename](file:///path/to/file)`）。
- **保留完整性**：編輯現有檔案時，維持既有代碼風格與非相關註解，不無故刪減無關程式碼。
